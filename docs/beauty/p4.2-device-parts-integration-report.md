# P4.2 — integração de FaceParts no dispositivo

Somente laboratório e diagnóstico. **`semanticReleasedFill=false`.** **`useMappedPartsForSemanticFill=false` no default.** Sem V2, sem mudança de amplitude, sem promoção do fill P3.

## O que mudou

A máscara nativa 6 classes (`FacePartsSegmentation`) continua a ser **pedida** para jaw/chin/v_face (P4.1). P4.2 liga o mapeamento real e a telemetria, mas **não aplica a máscara ao RGBA** até a flag explícita `FaceWarpV3Config.useMappedPartsForSemanticFill`.

| Flag | Default | Efeito |
|---|---|---|
| `silhouetteRequestsFaceParts` | `kDebugMode` | pede `FacePartsDetector` |
| `useMappedPartsForSemanticFill` | `false` | injecta mapped no compose/classificador |
| `semanticReleasedFill` | `false` | fill P3 same-class (não ligado) |

Mapeamento 6 classes → taxonomia P3 / parsing 19 (sem inventar ear):

| MediaPipe | Parsing / P3 |
|---|---|
| `background` | `background` |
| `hair` | `hair` |
| `bodySkin` | `neck` |
| `faceSkin` | `skin` |
| `clothes` | `cloth` / `clothing` |
| `others` | `others` / unknown |
| *(não existe)* | **`ear=0` sempre** |

`source=geometric` **não** é parsing semântico: `parsingStatus=unknown`. Só `mappedMulticlass` (máscara nativa não vazia) entra no compose, e só com a flag lab on.

## Distinção de estados (o iPhone já mostrou isto no P4.1)

O P4.1 pediu parts e **não** as passou ao compose. Por isso o log podia ter `roiPartsStatus=present` e ao mesmo tempo `parsingEmpty=true`. Isso continua correcto no default P4.2:

| Campo | Integração OFF (default) | Lab ON |
|---|---|---|
| `roiPartsStatus` | `present` (se a máscara nativa carregar) | `present` |
| `roiPartsSource` | `mappedMulticlass` | `mappedMulticlass` |
| `parsingStatus` | `unknown` | `present` |
| `parsingSource` | `none` | `mappedMulticlass` |
| `parsingEmpty` | `true` | `false` |
| `partsUsed` | `false` | `true` |
| RGBA | hash P0 | pode divergir (classificador vê parsing) |

Logs novos: `hairPx`, `bodySkinPx`, `faceSkinPx`, `clothesPx`, `backgroundPx`, `othersPx`, `earPx=0`, `ear=0`, `partsUsed`, `parsingStatus`, `dumpDir`.

## Protocolo no iPhone físico (mesmo input)

**Full restart** (`flutter run`). Hot reload não chega.

1. Foto do editor. `jaw=50`, chin/v_face/face_slim e resto a zero.
2. **Parts lab P4.2 desligado** (default). Um frame. Log esperado:
   - `roiPartsStatus=present`
   - `roiPartsSource=mappedMulticlass`
   - `parsingStatus=unknown` / `parsingEmpty=true` / `partsUsed=false`
   - seis contadores `*Px` reais do modelo 256×256
   - `ear=0`
   - `dir=` apontando para Documents/tmp, **não** `.cursor`
3. **Exportar dump** → pasta `_live/off`.
4. Ligar **Parts lab P4.2**. Mesma foto, `jaw=50`. Log esperado:
   - `parsingStatus=present` / `partsUsed=true` / `useMappedPartsForSemanticFill=true`
   - `semanticReleasedFill` continua `false`
5. **Exportar dump** → pasta `_live/lab`.

A cobertura das seis classes no dispositivo só é válida nestes dumps live. O harness macOS não corre MediaPipe.
